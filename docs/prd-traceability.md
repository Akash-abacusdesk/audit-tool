## Current Truth

**Scope change:** Vaultwarden is not part of this platform — an external microservice reached only through a private API client (PRD §3, §4.2). The original Task Portal (`apps/portal`) was removed from the repo entirely during the PRD rescope.

**Scope addition (outside the PRD, user-requested):** `apps/admin` is a new minimal Next.js admin UI added this session — not a PRD deliverable, a separate management surface talking to the existing REST API via a same-origin proxy (`next.config.ts` rewrites, no CORS). Covers: findings (list/filter/detail/status), scan runs, JIT approval/revoke, and Telegram alert-binding management. Built with Tailwind v4 + `motion`; visually verified via a real headless-Chrome screenshot of the login page (dark glassmorphism, gradient accents). Dashboard pages compile clean under the same design system but were not individually screenshotted (would need a scripted authenticated browser session — deliberately not built since it would require a debug auth-bypass the auto-mode classifier correctly flagged as a security weakening; reverted immediately).

The project is not yet 100% PRD-complete, but is substantially further along than earlier snapshots of this doc claimed. Fixed this session: a silently broken build (stale dist/.tsbuildinfo cache masked 20 TypeScript errors), S11/S14 routes that existed with tests but were never registered on the server, and a deep-audit pipeline redesigned from enqueue-all-7-upfront-with-a-monolithic-rerun to true per-stage pg-boss jobs (chained, idempotent, crash-safe resume).

All 7 S14 deep-audit stages are now real (not mocked), and actually verified against live Docker this session, not just unit-tested: Semgrep, Gitleaks, Lynis, testssl.sh, ZAP, and a new ClamAV scanner image were all run for real. That verification caught and fixed one real bug (the testssl.sh adapter assumed the wrong JSON shape). S11/S14/S15's stores are now PostgreSQL-backed (api_staging_runs, api_deep_audit_runs, api_secrets -- migration 009), verified with real inserts/transitions against live Postgres. Private-API clients exist for the external Vaultwarden and Telegram services. Vaultwarden hosting has been stripped from infrastructure/recovery-host in favor of real PostgreSQL WAL reception (pg_receivewal).

S11's staging provisioner is now real: `apps/api/src/staging/provisioner.ts` stands up an actual ephemeral WordPress+MySQL pair per run (own docker network, host-assigned port), consumed by real pg-boss job handlers (`apps/api/src/staging/worker.ts`) instead of sitting unconsumed. S12 functional/visual validation is real too: `apps/api/src/staging/validate.ts` runs an actual headless Chrome against that environment over its own docker network — real HTTP check, real DOM inspection for fatal errors, and a real screenshot byte-diffed against the previous run. S13's `update.stage` job now reuses the same provisioner to run a real functional check before reporting the state machine's staging_passed/staging_failed outcome. All three were verified live this session (real containers created, checked, and torn down with zero leftovers) — not just unit tests.

S13's `update.snapshot`/`update.promote` are now real too, against a stand-in: `apps/api/src/update/production.ts` stands up a long-lived (not torn down after each run) WordPress+MySQL pair per environment — wp-content in a named docker volume so it survives across calls, installed through the real 5-minute-install wp-cli flow so it's an actually operable site, not an empty shell. `update.snapshot` takes a real restore point (mysqldump of the DB + tar of wp-content, written to local disk); `update.promote` runs a real wp-cli `core update`/`plugin update` against it and fails closed (logs, attempts `promote_failed`) if the command fails — verified live this session end to end, including a real `wp core update` hitting wordpress.org and a real fail-closed rejection of a nonexistent plugin. This is not a real production host (Phase 3 still needs one — see docs/ops/phase3-readiness.md), but the entire code path is now real and testable; swapping in a real host later only touches `production.ts`.

Remaining gaps are genuinely live-infrastructure/credential work: real WordPress/Telegram/Git-provider/Vaultwarden endpoints, real fleet-shaped capacity numbers. See docs/ops/phase3-readiness.md.

## Hardening review (2026-09-29)

A security / scale / resilience / weight review was done and most findings fixed (see git history once committed). Corrections to the claims above:

- **S14**: the deep-audit *worker* was constructed with the in-memory store while routes wrote to Postgres, so a run created over HTTP could not be found by the worker ("run not found", swallowed). Fixed (`main.ts` uses `PgDeepAuditStore`, failures now rethrow for pg-boss retry). The "all 7 stages verified live" statement covered the adapters, not this API-to-worker path; the HTTP path has not been re-run live with real scanners since the fix.
- Verified live this round (real Postgres 17 + Docker in WSL): migrations 001-018; auth, authz-matrix, git-sync, scheduler integration suites; s8/s9/s7 abuse batteries; acceptance subset 6/6; staging provision -> ready -> destroy through the API and pg-boss with a transactional job send; hardened chrome visual suite; update stand-in snapshot + fail-closed promote; TOTP MFA flow.
- Still open: audit-table partitioning (retention is `apps/api/tools/audit-prune.mjs`), scanner-image slimming (would invalidate `scanner/build-record.json`), scanner worker integration suite (needs a Docker Desktop host with the images), the GitHub Actions workflow has not run on GitHub, WordPress plugin change for JIT redeem (`token` instead of `token_hash`) is untested (no PHP here).
